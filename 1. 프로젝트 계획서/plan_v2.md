# 어때? (EOTTAE) — 프로젝트 계획 v2
작성일: 2026-10-29 / 상태: 중간 점검 1차 — 공통 틀·통합 홈 완료, 매칭 화면은 데모 데이터로 동작 (실데이터 연결 전)
이전 버전: `plan_v1.md` (2026-10-26, 계획 v1 업로드본)

## 한 줄 소개
첫 매칭부터 데이트·소모임, 모바일 청첩장까지 관계의 여정을 하나로 잇는 PWA 웹앱 「어때?」

## 목표
- 웹사이트/PWA 1개 + 공통 브랜딩·회원·설정·안전·디자인 시스템 1개
- 사용자 여정으로 연결되는 서비스 3개:
  ① 매칭 `/match` (1차 MVP, 이번 개발 대상)
  ② 데이트·소모임 `/activities` (2차, 이번엔 준비중 페이지)
  ③ 모바일 청첩장 `/invitations` (3차, 이번엔 준비중 페이지)

## 누구를 위한 것인가
- 새 인연을 찾고, 그 관계를 데이트·모임·결혼 준비로 이어 가고 싶은 10~40대
- 로맨스 매칭·1:1 채팅은 만 19세 이상 성인 확인 사용자 전용

## 이번 버전 범위 (1차 MVP)
1. **통합 홈 + 공통 PWA 틀** — 로고·내비게이션·로그인·6가지 테마(라이트·다크·시스템 등)·오프라인 화면. 2차·3차는 실제로 들어가 볼 수 있는 준비중 페이지로 안내(실기능 미출시를 솔직히 표시)
2. **매칭** — 취향·가치관 프로필, 문답·공통 질문으로 궁합 확인, 카드 추천, 쌍방 관심 시 매칭 → 1:1 채팅
3. **안전 장치** — 성인 확인 전·차단 상태면 매칭·채팅 진입 거부, 신고·차단, 차단·탈퇴 사용자는 추천·대화에서 제외, 남의 데이터는 DB 권한 규칙(RLS)으로 차단

## 완성의 기준
- 배포 주소(시연용 테스트 인증을 공개 배포에서 켜지 않기로 하면 로컬 시연 환경)에서 서로 다른 두 계정이 회원가입 → 프로필 작성 → 추천 → 쌍방 관심 → 1:1 채팅까지 **실제 데이터로** 끊김 없이 진행
- 성인 확인 전이거나 차단된 사용자가 매칭·채팅에 접근하면 거부됨
- 차단한 상대는 추천과 대화 목록에서 사라짐
- 위 과정을 캡처와 테스트 기록으로 증빙
- 성인 확인은 시연용 테스트 인증까지 — 정식 인증 업체 연동은 실제 출시 전 과제(DEC-01)

## 역할 분담 (4인 팀)
- 김민기: 전체 기본 틀·공통 사이트 구조·홈/내비게이션/테마·로고·PWA shell·문서 통합·배포·협업 자동화·Supabase 프로젝트 소유(키·배포 Secrets·운영 DB 마이그레이션 적용)
- 오하율: 매칭 프로필·취향·추천 UI/UX 및 접근성
- 주한태: 인증·성인 확인·매칭 API·DB·RLS 보안 (스키마·정책 주도, 로컬 Supabase에서 개발)
- 손준혁: 1:1 채팅·신고·차단·통합 품질 검증/시연 증빙
- Supabase 조직: 오하율·주한태·손준혁 모두 Developer로 참여 — 급할 때 서로 대신 작업, DB 변경은 마이그레이션 PR로만 (ADR-005)

## v1 → v2 바뀐 점과 이유
- **핵심 기능 3번**: "준비중 페이지" → "안전 장치". 준비중 페이지는 1번(공통 틀)에 합침 — 안내 화면보다 성인 확인·신고·차단이 이 앱의 차별점이자 출시 Gate라서
- **완성의 기준**: "구현 화면 5장 이상" 삭제(이미 19장 확보로 기준 역할을 못 함) → 두 계정 실데이터 흐름·권한 거부·차단 반영처럼 확인 가능한 조건으로
- **성인 확인 표현**: 정식 인증 업체가 미정(DEC-01)이라 "시연용 테스트 인증까지"로 범위를 밝힘
- **테마**: 라이트/다크 → 6가지 테마 + WCAG AA 대비 전수 보정 (PR #18)
- **서버 구조**: Supabase + GitHub Pages 확정, Supabase 프로젝트는 김민기 소유·팀원 Developer (ADR-005, DEC-08) — Pages는 정적 배포라 API 서버를 돌릴 수 없어서
- **AI 코드 리뷰**: Devin → 로컬 Grok (2026-10-28) — Devin 크레딧 과금, Grok은 기존 구독 안에서 처리. 로그인 정보는 GitHub에 올리지 않고 김민기 PC에서만 실행
